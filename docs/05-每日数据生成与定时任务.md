# 每日数据生成与定时任务执行规程

版本 1 · 2026-11-10。供后续定时 Agent 直接执行。当前是静态原型数据链路，未安装定时任务、GitHub Actions、LLM 调度器或 Vercel 部署。本文件规定任务行为，不表示任务已启用。

## 1. 任务目标与入口

每天北京时间 07:00 前生成一期有来源、可阅读、可校验的 AI / GitHub 简报，提交至本仓库。运行时不调用模型、GitHub API 或外部搜索；网页由静态文件组成。保持用户已确认的 v0.6 玻璃磨砂设计，不在每日任务中改 UI、设计 token 或产品规则。

先读 `AGENTS.md`、`docs/01-项目规约.md`、`docs/00-项目蓝图.md`、本文。任务参数见 `config/daily-task.json`，来源白名单见 `config/sources.json`。不要读取 `prototype/demo-data.json` 生成新闻；它只保留作历史原型样例，不进入页面、历史去重或周观察。

当前可运行命令只有 Python 标准库脚本与 Node 语法检查；仓库尚无 package.json、Astro、Zod 和 pnpm 命令。未来生产工程接入时，以 `src/content.config.ts` 的 Zod schema 为唯一源，同时迁移校验器和采集器，不能长期维护两套独立生产 schema。本轮 Python 校验器是原型数据契约的过渡实现。

## 2. 触发与时间

| 任务 | UTC cron | 北京时间 | 行为 |
| --- | --- | --- | --- |
| 主刊 | `17 22 * * *` | 次日 06:17 | 最近 24 小时事件，07:00 前完成 |
| 午间勘误 | `43 4 * * *` | 当日 12:43 | 检查最近 6 小时的重要纠错，只 append amendments |
| 手动 / 补跑 | workflow_dispatch 或外部 Agent 手动触发 | 显式指定 | 指定日期和截止时间，标记补刊 |
| 备用触发 | repository_dispatch | 由监控调用 | 与主刊共享锁和幂等检查 |

定时按 UTC 配置，目标日期按 `Asia/Shanghai` 算。主刊 22:17 UTC 对应北京次日，不能使用 UTC 日期作刊期。Node 中使用 `new Intl.DateTimeFormat('en-CA',{timeZone:'Asia/Shanghai',year:'numeric',month:'2-digit',day:'2-digit'}).format(new Date())`；Python 可用 `datetime.now(ZoneInfo('Asia/Shanghai')).date().isoformat()`。

每次启动先固定 `cutoff`，主刊窗口为 `[cutoff-24h, cutoff]`，不随采集过程漂移。补刊使用 `manual-backfill`，写明实际窗口、生成时间与原因，不伪装为当天 07:00 已出刊。2026-11-10 为首期补刊；日期精度的官方稿按覆盖日期纳入，保留 day 精度，不能补造时分秒或时区。秒级来源严格检查窗口；day 来源必须注明可能跨精确窗口的限制。

调度是尽力触发，不保证准点。将来部署 Actions 时：workflow 在 main，最小权限 `contents: write`，`timeout-minutes: 20`，单一 concurrency group 串行写库且 `cancel-in-progress: false`。主触发、补跑和勘误共用锁；不要让两个 Agent 同时改同一期。外部 Agent 调度器需提供同等的锁、超时和三重触发能力。

## 3. 收集与编辑

1. 记录初始 `git status --short`、分支和远端提交。专用干净 checkout 上开始；有无关改动就保留，不能 reset、clean、stash 或整库暂存。先确认本地 main 与 origin/main 一致。
2. 搜索只用于发现线索。打开官方公告、仓库 README / LICENSE / release、论文原文核对全文和时间。聚合日报不能作为唯一证据。新增来源先审查域名并同步白名单；不通过每日数据提交偷偷放宽规则。
3. 优先最近 24 小时的重要变化，通常 4–6 条，宁可少而准，不为凑数写旧闻。用 GitHub API 或官方 release 交叉核对版本、发布时间与仓库身份。不能把仓库最近 pushed_at 当作新版本发布时间。
4. 每条先给结论，再交代它是什么、解决什么、效果和原理。why 写结构性变化，避免宣传语。保留 3–4 条 facts、2–4 个 scenes、event、caveat 和至少一个原文来源。厂商自测、路线图、未复跑数据、付费/审核访问要明确标注。禁止绝对化承诺、无来源数字、全文转载、把传闻当发布。
5. `brief` 按顺序与 items 的 id 一一对应，不能生成另一套选题。标题高亮只用现有 mark 白名单；正文不用任意 HTML。图片不能补造数据，也不能以吉祥物代替信息。
6. 与 `content/history.json` 的 URL / 指纹 / 事件语义比对。不同 URL 复述同一事件也算重复，脚本无法替代语义审稿。同一项目可以在新事件出现时再次收录，并解释新增变化。
7. 来源必须可读且链接指向原文；记录 `checkedAt` 和核验渠道。HTTP 失败不能写成 HTTP 成功；可用浏览器/联网工具读全文并记录例外。仅搜索摘要不足以支持关键事实。无法核实的条目移除或降级，不杜撰。

## 4. 文件契约与样本

当前完整可用样本是 `content/days/2026-11-10.json` 和 `content/projects/2026-11-10.json`，复制结构、替换内容与日期，不复制事实。字段要求由 `scripts/validate-content.py` 执行，展示适配在 `scripts/content_data.py`。

| 文件 | 必须包含 |
| --- | --- |
| `content/days/<date>.json` | schemaVersion=1、date、timezone、no、status、generatedAt、window、headline、short、lede、themes、items、brief、amendments |
| `items[]` | 唯一 id、cat、title、verdict、why、facts[3–4]、scenes[2–4]、event、caveat、sources[≥1] |
| `sources[]` | id、url、title、publisher、publishedAt、publishedPrecision(day/second)、checkedAt、verification |
| `content/projects/<date>.json` | schemaVersion、date、collectedAt、projects[]；每个项目的 name、lang、license、oneline、problem、scenes、notFor、whyToday、whyWeek、topics、day、week、alt、sources |
| `content/snapshots/<date>-<owner>--<repo>.json` | repo、collectedAt、apiUrl、stars、language、license、pushedAt、archived、description；本次 GitHub API 的必要摘录 |
| `content/sources/<date>.json` | 来源核验清单、checkedAt、渠道与失败/例外说明；不能存凭据和有访问令牌的 URL |
| `content/history.json` | 从已确认刊期生成的 itemId、date、规范化 URL、SHA-256 指纹 |
| `content/days/<date>.md` | 由生成器输出，与网页同源，含来源和勘误，不手改 |

no 从上一真实刊期递增，首期为 1。status 可为 ready 或 degraded；degraded 必须说明缺失与原因，仍须满足已收录条目的事实硬要求。无合格内容禁止生成空刊，也不能覆盖上一期。

项目先写用途再放数字。许可证以实际 LICENSE 与适用范围为准，不能仅按语言推断；例如 Claude Code 不是 MIT。累计 star 是采集时快照，不是上榜证明。日增量=当前星标减约 24h 前同一基准时间快照；周增量减约 7 天前快照，需保存 baselineAt / baselineFile 和实际间隔；本次不具备这类基线，统一 null，禁止填 0 或编折线。负增长按实际值显示，不截为零。项目档案允许背景补充，但不能称为当天新发布。周观察只使用近七天的真实刊期，历史不足就说明不足。

## 5. 执行与质量闸门

由 Agent 生成 JSON，写到临时路径；审核后原子移动到目标位置。已存在且已提交的刊期不改正文，不重抓后覆盖项目快照。先运行内容校验，确认通过再更新去重历史与网页：

```sh
python3 scripts/validate-content.py --write-history
python3 scripts/validate-content.py
python3 scripts/build-prototype.py
python3 scripts/check-prototype.py
node --check prototype/app.js
```

可额外运行 `python3 scripts/validate-content.py --check-links` 检查实时 HTTP。该命令失败必须处理：用浏览器读取原文，记录失败类型、核验渠道和时间，再做人工事实审查；不能宣称脚本通过。GitHub API 被限流时尊重 Retry-After、最多重试两次，不绕过限流；必要时使用已配置的只读令牌，禁止打印或提交令牌。

当前校验覆盖必填、字段数量、时间窗口、来源白名单、brief 对齐、重复事件指纹、与 HEAD 的正文不变性、项目快照及 HTML 链接/体积。它不能证明新闻真实、语义不重复、全部无障碍、Lighthouse ≥95 或线上部署成功；这些必须另验。未来 pnpm 工程建立后追加 `pnpm typecheck && pnpm lint && pnpm daily:validate && pnpm build`，目前不能写“通过”。

检查差异后本地预览：首页、来源展开、项目日周切换、往期搜索、分享图片/文字、手机溢出。浏览器检查完 `agent-browser close`，停止任务自己启动的预览服务器，确认没有留下后台进程。不关闭用户其他浏览器或服务。

## 6. 发布后纠错与幂等

首次刊期提交后正文不可改写；只在原刊 `amendments[]` 末尾增加 `{itemId,text,createdAt}`，既有项不删不改。补充说明要引用原文链接（可写入 text），并解释纠正内容。当前页面和 Markdown 输出勘误；来源核验清单追加核验记录。午间不偷偷加正文新条目；新事件放下期。

生成器确定性输出：相同输入字节重复运行不得产生新差异，不更新“当前时间”凑提交。采集失败保留上一有效刊期，不发布空页；失败状态写外部运行日志，不能篡改上一期事实。health.json 与死人开关尚未实现；将来仅在校验、生成、目标提交成功后更新成功时间并 ping 配置在 secret 中的地址，失败不发成功信号。没有配置的 secret 不作硬编码替代。

## 7. Token 与超时预算

配置预算按北京自然日聚合，所有触发和重试共用：输入最多 120,000 token，输出最多 20,000 token，每阶段最多尝试两次，总任务 20 分钟。小模型抽取，旗舰模型主编与终审；具体供应商/模型用执行环境配置，不写死过时型号。调度器持久记录实际 usage；本仓库没有自动计量器。无法取得可靠计量就不能宣称硬预算已生效，执行器必须先建立用量台账，超限停生成并保留上一期。不得提交模型密钥、调度器凭据、原始完整网页或私有材料。

## 8. 提交与推送

只暂存本次目标日期 JSON / Markdown、项目和快照、核验记录、history，以及生成器实际改变的 `prototype/` 页面与资源；不要 `git add .`。每日任务不提交 `.idea`、缓存、截图、临时文件或无关源码。增量更新一般不包含设计/文档修改。提交前审查 `git diff --cached --stat` 与 `git diff --cached --check`，确认新文件和删除均属于本次内容。

提交格式：`chore(daily): YYYY-MM-DD [skip ci]`。无差异不 commit。任务授权范围含推送时，再 `git push origin main`；只授权本地生成/提交时不得擅自推送。push 被拒绝先 fetch，在干净 checkout 中检查并解决目标内容冲突、重新生成验证；禁止 force push，禁止把未审核的第三方改动带入。已存在同日主刊则只做校验或 append 勘误。`[skip ci]` 会影响某些 Actions，未来部署流水线须显式验证这一行为，不能假设它仍触发所有部署检查。

任务完成输出：目标日期/时区、真实条目/项目数、实际采集窗口、降级项、已运行校验、commit hash、是否推送、是否部署、后台进程清理状态。不能以“写了规则”代替“定时任务已安装”。

## 9. 给后续 Agent 的任务提示

> 在 daily-ai 仓库执行每日内容任务。先阅读 AGENTS.md 与 docs/05-每日数据生成与定时任务.md，按 Asia/Shanghai 确定目标日期与固定采集截止时间。只从白名单官方原文和 GitHub API 采集，生成规范 JSON 与快照，去重并标注事实边界；不使用 prototype/demo-data.json。保留已提交刊期正文，缺历史统计填 null，失败保留上一期。运行内容校验、静态生成和检查，核对页面与来源后按 chore(daily): <date> [skip ci] 提交本次内容。是否推送按本次调度授权。报告实际校验、提交/推送状态，不改 UI、不新增后端、不创建账户、不泄露凭据；结束前关闭本任务启动的浏览器和服务。
